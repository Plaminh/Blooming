# Blooming database baseline

PostgreSQL baseline schema for the Blooming desktop planner MVP.

This directory intentionally separates the schema by table. Run `install.sql` with `psql` to install them in the correct foreign key order.

## Scope and file order

- `00_init.sql`: Extensions and common functions.
- `tables/*.sql`: one file per table, with numeric prefixes defining installation order.
- `99_seed.sql`: Static seed data (e.g. plant catalog) inserted after the tables are created.

## Install / Recreate Database

The installer uses the PostgreSQL `psql` client and the `\ir` directive to load the scoped files relative to `install.sql`.
**Warning: The following commands will completely delete the existing development database and all its data.**

To recreate the development database from scratch using Docker Compose:

```bash
# 1. Stop and delete the database container and its persistent volume
docker compose down -v

# 2. Start a fresh database container
# Docker will automatically run docker/01_install.sql -> database/install.sql
docker compose up -d
```

## Validate

After installation, run the transactional smoke test. It inserts one connected record through every scope and then rolls everything back.

```bash
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/database/tests/00_schema_smoke_test.sql'
```

## Design rules

- IDs are UUIDs generated by PostgreSQL.
- Timestamps are `TIMESTAMPTZ` and should be written/read in UTC.
- `daily_plans.plan_date` is the user's local calendar date.
- Durations are integers: task estimates use minutes; timer-accurate focus fields use seconds.
- Status fields use `VARCHAR` plus `CHECK` constraints so they remain easier to evolve than native PostgreSQL enums.
- `tasks` store intended work, `plan_blocks` store scheduled time, and `focus_runs` store actual execution.
- AI payloads and plan snapshots may use `JSONB`; query-critical state remains in typed columns.
- Widget position and window visibility are device-only. Autostart and always-on-top preferences are saved in user_settings and applied natively.
- Completed history is immutable at the application layer. Re-planning updates future blocks and appends a `plan_revisions` record.
- Tasks, plans, focus runs, and goals use lifecycle statuses instead of physical deletion. Hard deletion is reserved for full account teardown and test data.
- Every resource reward has a unique `idempotency_key`, preventing duplicate progress even when a completion request is retried.
