# Blooming database baseline

PostgreSQL baseline schema for the Blooming desktop planner MVP.

This directory intentionally separates the schema by product scope. Run the
files in numeric order, or run `install.sql` with `psql`.

## Scope and file order

| File | Scope |
| --- | --- |
| `00_extensions.sql` | PostgreSQL extensions used by the schema |
| `01_users_and_auth.sql` | Accounts, user settings, and refresh-token sessions |
| `02_goals_and_milestones.sql` | Long-term goals and ordered milestones |
| `03_planning_chat.sql` | Planning conversations and messages |
| `04_tasks_and_dependencies.sql` | Intended work and direct task dependencies |
| `05_daily_planning.sql` | Daily plans, availability, scheduled blocks, and revisions |
| `06_focus.sql` | Pomodoro/focus runs and their state-transition history |
| `07_reminders.sql` | Reminder definitions, unread state, and user actions |
| `08_heart_and_garden.sql` | Water/Leaves reward ledger, plant catalog/ownership and garden state |
| `09_updated_at_triggers.sql` | Automatic maintenance of mutable `updated_at` columns |
| `10_indexes.sql` | Uniqueness and query-performance indexes |

The installer creates 22 tables. Feature 019 directly updates the authoritative
CREATE TABLE files for task category, garden growth points and reminder lead
minutes; it adds no Alembic revision. Existing databases are not altered by
editing these files or rerunning CREATE TABLE IF NOT EXISTS. Apply the
[additive update statements](../specs/019-cleanup-integration/quickstart.md#existing-local-databases)
manually to an existing database. Do not reset the developer database or volume.

Feature 024 adds fixed-precision weather coordinates and scene season to
`01_users_and_auth.sql`. Existing databases require the separate
[additive update statements](../specs/024-weather-environment-reliability/quickstart.md#existing-databases);
the bootstrap installer does not alter an already-created table.

## Install

The installer requires the PostgreSQL `psql` client because it uses `\ir` to
load the scoped files relative to `install.sql`.

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f database/install.sql
```

For the existing Docker container, copy the directory into the container and
execute the installer there. Replace the database user and name if the Compose
configuration uses different values.

```bash
docker cp database blooming-postgres:/tmp/blooming-database
docker exec blooming-postgres \
  psql -U blooming -d blooming -v ON_ERROR_STOP=1 \
  -f /tmp/blooming-database/install.sql
```

For a brand-new PostgreSQL container, the whole `database` directory may be
mounted at `/docker-entrypoint-initdb.d`. PostgreSQL's entrypoint will execute
the root `install.sql`; the numbered files remain inside `migrations/` so they
are not executed twice.

## Validate

After installation, run the transactional smoke test. It inserts one connected
record through every scope and then rolls everything back.

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f database/tests/00_schema_smoke_test.sql
```

## Design rules

- IDs are UUIDs generated by PostgreSQL.
- Timestamps are `TIMESTAMPTZ` and should be written/read in UTC.
- `daily_plans.plan_date` is the user's local calendar date.
- Durations are integers: task estimates use minutes; timer-accurate focus
  fields use seconds.
- Status fields use `VARCHAR` plus `CHECK` constraints so they remain easier to
  evolve than native PostgreSQL enums.
- `tasks` store intended work, `plan_blocks` store scheduled time, and
  `focus_runs` store actual execution.
- AI payloads and plan snapshots may use `JSONB`; query-critical state remains
  in typed columns.
- Widget position and window visibility are device-only. Autostart and
  always-on-top preferences are saved in user_settings and applied natively.
- Completed history is immutable at the application layer. Re-planning updates
  future blocks and appends a `plan_revisions` record.
- Tasks, plans, focus runs, and goals use lifecycle statuses instead of physical
  deletion. Hard deletion is reserved for full account teardown and test data.
- Every resource reward has a unique `idempotency_key`, preventing duplicate
  progress even when a completion request is retried.
