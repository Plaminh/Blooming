# Feature Specification: Mr. Bloom Planning and Draft Review Flow

**Feature Branch**: `[branch-name]`

**Created**: 2026-09-14

**Status**: Draft

**Input**: User description: "Create one new, independent specification for implementing the complete Blooming **Mr. Bloom planning and draft-review flow** represented by these four screens..."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Conversational Planning Interface (Priority: P1)

As a user, I want to chat with Mr. Bloom so that I can describe what I want to achieve and get planning assistance.

**Why this priority**: The chat interface is the core entry point for all AI-assisted planning.

**Independent Test**: Can be fully tested by verifying that the chat interface renders correctly, accepts user input, prevents empty submissions, and displays deterministic mock responses from Mr. Bloom.

**Acceptance Scenarios**:

1. **Given** the Mr. Bloom view is open with no active draft, **When** the page loads, **Then** the chat interface is displayed on the left and a "Live Draft" placeholder is displayed on the right.
2. **Given** the chat input is empty or contains only whitespace, **When** the user attempts to submit, **Then** the submission is prevented.
3. **Given** a valid message in the input, **When** the user submits via Enter key or send button, **Then** the message appears in the chat history and a simulated response is triggered.

---

### User Story 2 - Roadmap Draft Review (Priority: P1)

As a user, I want to review a proposed roadmap draft generated by Mr. Bloom so that I can adjust milestones before saving it to my goals.

**Why this priority**: Enables long-term goal planning, which is one of the two primary planning modes.

**Independent Test**: Can be tested by loading the Roadmap Draft mock state and verifying the rendering, selection, and interactive controls (edit, delete, add, discard, save).

**Acceptance Scenarios**:

1. **Given** a mock roadmap generation response, **When** the draft is ready, **Then** the Roadmap Draft panel replaces the placeholder on the right, displaying milestones and target dates.
2. **Given** an active roadmap draft, **When** the user clicks "Discard", **Then** the draft is cleared without being saved.
3. **Given** an active roadmap draft, **When** the user clicks "Save to Goals", **Then** the draft is successfully accepted in the local view-model.

---

### User Story 3 - Today Draft Review (Priority: P1)

As a user, I want to review a list of extracted tasks for today before generating a detailed timeline.

**Why this priority**: Task extraction and duration estimation are critical prerequisites for daily schedule generation.

**Independent Test**: Can be tested by loading the Today Draft mock state and verifying task cards, duration adjustments, priority dropdowns, and transitions.

**Acceptance Scenarios**:

1. **Given** a mock daily plan generation response, **When** the draft is ready, **Then** the Today Draft panel displays extracted tasks with editable durations and priorities.
2. **Given** an active today draft, **When** the user modifies a task's duration or priority, **Then** the shared local draft model is updated.
3. **Given** an active today draft, **When** the user clicks "Generate Timeline", **Then** the view transitions to the Timeline Draft state.

---

### User Story 4 - Timeline Draft Review (Priority: P1)

As a user, I want to review a generated hour-by-hour timeline schedule so that I can ensure it's realistic before committing it to my day.

**Why this priority**: The visual timeline is the ultimate output of the daily planning flow, allowing the user to visualize breaks and task placement.

**Independent Test**: Can be tested by loading the Timeline Draft mock state and verifying the rendering of hours, task cards, breaks, and buffers.

**Acceptance Scenarios**:

1. **Given** the user proceeds from the Today Draft, **When** the timeline is generated, **Then** the Timeline Draft panel displays a vertical schedule with times and task blocks.
2. **Given** the Timeline Draft view, **When** the user clicks "Back to Tasks", **Then** the view returns to the Today Draft preserving all task data.
3. **Given** an active timeline draft, **When** the user clicks "Save to Today", **Then** the timeline is accepted in the local view-model.

### Edge Cases

- What happens when the user navigates away from Mr. Bloom while a draft is active? The draft should remain available in local state if they return, or prompt before discarding.
- How does the system handle rapid sequential submissions? The input should be disabled while waiting for a response.
- What happens when a draft task's duration is set to 0 or an invalid number? The input should validate and enforce minimum/maximum boundaries.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST render the shared application shell, title bar, and sidebar, with the "Mr. Bloom" navigation item active.
- **FR-002**: The system MUST render the Mr. Bloom chat panel with a conversation history, avatars, message metadata, and a composer input.
- **FR-003**: The system MUST prevent submission of empty or whitespace-only messages.
- **FR-004**: The system MUST support submitting messages via the Enter key and the on-screen send button.
- **FR-005**: The system MUST implement a deterministic local mock to simulate AI responses and draft generation when real backend AI is unavailable.
- **FR-006**: The system MUST maintain a shared, typed local draft view-model that serves all draft views (Roadmap, Today, Timeline) without redundant hardcoded data.
- **FR-007**: The system MUST render the "Live Draft" placeholder state when no draft is active (`chat-overall.png`).
- **FR-008**: The system MUST render the "Roadmap Draft" view (`plan-draft.png`) with functional edit/delete/add controls.
- **FR-009**: The system MUST render the "Today Draft" view (`today-draft.png`) with functional duration inputs, priority dropdowns, and delete controls.
- **FR-010**: The system MUST render the "Timeline Draft" view (`timeline-draft.png`) displaying tasks scheduled against hours, breaks, and buffers.
- **FR-011**: The system MUST allow seamless navigation back and forth between related draft states (e.g., Today Draft <-> Timeline Draft) while preserving data.
- **FR-012**: The system MUST successfully process acceptance ("Save") and cancellation ("Discard") actions by updating the local view-model state.
- **FR-013**: The system MUST use reusable components (atoms, molecules, organisms) following the project's Atomic Design guidelines, without monolithic markup copying.

### Key Entities

- **Chat Message**: Represents a single message (id, role: user/assistant, content, timestamp).
- **Draft Session**: The container for the current draft state, referencing a specific draft type.
- **Roadmap Draft**: Contains the overarching goal and a list of milestones (id, title, target_date).
- **Today Draft**: Contains available hours and a list of extracted tasks (id, title, duration_min, priority).
- **Timeline Entry**: A scheduled block in the timeline view (id, type: task/break/buffer, title, start_time, end_time, duration_label).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: The application builds successfully and all Svelte and TypeScript checks pass.
- **SC-002**: All existing tests remain passing.
- **SC-003**: New relevant interaction tests provide coverage for chat submission, draft generation, preview switching, task selection, revision, cancellation, and acceptance.
- **SC-004**: Each of the four screens is rendered at its native reference viewport size and visually matches the provided references.
- **SC-005**: A screenshot is captured for each implemented state and compared side-by-side with its corresponding reference to ensure layout, typography, colors, and spacing are accurate.
- **SC-006**: The browser console and terminal contain no new relevant errors or warnings.
- **SC-007**: No runtime code imports anything directly from `removed reference artwork`.

## Assumptions

- Backend AI integration, API development, and actual database persistence are out of scope for this feature.
- Deterministic, hardcoded local fixtures or view-models will simulate all responses and generation logic.
- Authentication changes are out of scope.
- Svelte, SvelteKit, and Tauri are the established technologies to be used.
- All required theme tokens, fonts, shared app shell components, and icons either already exist or can be built using existing CSS/SVG conventions without breaking the design system.
